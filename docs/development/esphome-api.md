# ESPHome native API server (`webos-esphome-api`)

Roadmap step 1.3. The crate [`crates/esphome-api`](../../crates/esphome-api) implements the device side of the ESPHome native API. Home Assistant's ESPHome integration connects to it and creates an Assist satellite ([ADR 0001](../decisions/0001-esphome-native-api.md)). Wake word, STT, conversation and TTS run in HA ([ADR 0003](../decisions/0003-server-side-wake-word-for-mvp.md)). The state machine and the public API are documented in the crate docs (`src/lib.rs`, `cargo doc -p webos-esphome-api`).

**Status (2026-11-02):** tested against aioesphomeapi 46.6.0 acting as HA (on the host, under qemu-arm, and on c3-a inside `webos-satellite`). It also carried full pipeline runs with the owner's real HA pipeline through the HA bridge. HA's own ESPHome integration has **not** connected to it yet, because HA cannot reach the TV's network ([P1 HA integration](../discovery/c3-a/P1-ha-integration.md), [P1 TV live](../discovery/c3-a/P1-tv-live.md)).

## Pinned protocol sources

| Item | Version | Use |
| --- | --- | --- |
| `api.proto`, `api_options.proto` | ESPHome 2026.10.1, vendored in `crates/esphome-api/proto/` (MIT, see `LICENSE-ESPHOME-MIT`) | Message definitions. No ESPHome C++ (GPLv3) was ported. |
| aioesphomeapi | 46.6.0 (the version HA 2026.10.4 pins) | Behaviour reference and the fake-HA test harness |
| HA | 2026.10.4 `components/esphome` | Behaviour reference (source reading only) |

Code generation: `build.rs` compiles the proto with `protox` (pure Rust, so no `protoc` is needed on the build host) and `prost-build`. It also extracts the `option (id)` message type ids from the proto text into `ApiMessage` impls. `prost` drops custom options, so this step is needed. Noise uses `snow` with only the ChaChaPoly, SHA256, 25519 and getrandom features. Its `std` feature would pull in `ring`, a C library, so it is left off.

## Decisions taken in this crate

- **API version 1.14** in `HelloResponse`. HA accepts device major version 1 or 2. aioesphomeapi 46.6.0 reads `voice_assistant_feature_flags` from `DeviceInfoResponse` for 1.10 to 1.14. From 1.15 on it expects `DeviceCapabilitiesResponse`, which the crate answers anyway. From 1.14, a missing `object_id` is tolerated, but the crate sets it regardless.
- **Voice feature flags** are configurable (`Config::voice_features`). The default is `VOICE_ASSISTANT | SPEAKER | API_AUDIO | ANNOUNCE` = 23:
  - With SPEAKER, HA streams the TTS reply as 16 kHz mono s16le PCM over the API, between the `TTS_STREAM_START` and `TTS_STREAM_END` events. The PCM chunks are 512 samples and carry no WAV header. The owner's HA builds media URLs from the pod IP, which the TV cannot reach (orchestrator note, [integration notes](../research/ha-esphome-integration-notes.md)).
  - Without SPEAKER, HA sends `TTS_END{url}` and the app fetches it (`AppEvent::TtsUrl`). After playback the device sends `VoiceAssistantAnnounceFinished`.
  - `START_CONVERSATION` (32) is implemented but off by default (see [START_CONVERSATION status](#start_conversation-status)).
  - `TIMERS` (8) is off by default in the API crate; the satellite turns it on by default (see [Timers](#timers)).
  - `MULTI_CHANNEL_AUDIO` (64) is rejected by config validation because it is not implemented.
- **Request flags:** `USE_WAKE_WORD` (2) is set for wake word runs. `USE_VAD` is never set, because HA 2026.10.4 ignores it.
- **Entities:**
  - Optional, set by the application in `Config`: a diagnostic `text_sensor` "TV power state" (`power_sensor`, fed by `AppCommand::SetPowerState`) and configuration `select` entities (`selects`, state by `AppCommand::SetSelect`, HA's choice by `AppEvent::SelectChanged`; an option outside the list is answered with the current state).
  - `AppCommand::Resumed` (after a system suspend): the server pings HA and drops the connection without an answer within 5 s, re-announces mDNS and re-arms a wake word waiting out a retry backoff.
  - One built-in `media_player` (object id `media_player`; application-owned, control-only players can be added, below). Its single ANNOUNCEMENT format is `flac`, 22050 Hz, 1 channel, 2 bytes. That is Piper's native rate, it streams well and symphonia can decode it. `sample_rate` is always set, to work around the HA 2026.10.4 bug. Its features are STOP, VOLUME_SET and VOLUME_STEP (4096 + 4 + 1024; HA 2026.10.4 takes them from `feature_flags`): the volume is the satellite's reply volume in percent (`AppCommand::SetVolume` at startup, `AppEvent::VolumeChanged` on a change from HA, steps of 5 %). In URL mode this format becomes HA's TTS format. In all modes it is the format of announcement media proxied through ffmpeg.
  - One "Mute microphone" switch, entity category config.
  - Generic application-defined entities, listed after the built-in ones in this order: `select`, `number`, `button`, `binary_sensor`, then `switch` and `text_sensor` (`Config::selects`, `numbers`, `buttons`, `binary_sensors`, `switches`, `text_sensors`; the generic switches are listed right after the mute switch and the text sensors right after the power state sensor). They are generic: the crate knows nothing about what they control.
    - **Identity.** Each has an `object_id` (`[a-z0-9_]`, at most 120 characters, unique across all entities including the built-in `media_player`, `mute_microphone` and `tv_power_state`) and a name. The entity key is the FNV-1 hash of the object id, as in ESPHome, so keys and HA entity ids stay the same across restarts and versions as long as the object id does. `Config::validate` rejects bad or duplicate ids, colliding keys and invalid number ranges (`ConfigError::InvalidEntity`).
    - **`NumberEntity`** (`ListEntitiesNumberResponse`): `min_value`, `max_value`, `step` (greater than zero), `unit`, `device_class`, `mode` (`proto::NumberMode`: auto, box, slider), `icon`, `entity_category` (`proto::EntityCategory`). State: `AppCommand::SetNumber { object_id, value: Option<f32> }`; `None` sends `missing_state` (HA shows unknown). HA's `NumberCommandRequest` becomes `AppEvent::NumberChanged { object_id, value }` only when the value is finite and within min to max; otherwise it is ignored with a log line and the current state is sent back. **The server never echoes a command as a state** (unlike `select`): the application acts (for example sets the TV volume) and reports the actual value with `SetNumber`, so HA shows what happened, not what was asked. `SetNumber` outside the range is ignored.
    - **`ButtonEntity`** (`ListEntitiesButtonResponse`): `icon`, `device_class`, `entity_category`; no state. `ButtonCommandRequest` becomes `AppEvent::ButtonPressed { object_id }`.
    - **`BinarySensorEntity`** (`ListEntitiesBinarySensorResponse`): `icon`, `device_class`, `entity_category`. State: `AppCommand::SetBinarySensor { object_id, state: Option<bool> }`, sent to HA on every change (an unchanged value is not repeated) and on every subscribe, `None` meaning `missing_state`. HA cannot change it.
    - **`SwitchEntity`** (`ListEntitiesSwitchResponse`): `icon`, `device_class`, `entity_category`. State: `AppCommand::SetSwitch { object_id, state: Option<bool> }` (an unchanged value is not repeated, `None` is `missing_state`). HA's `SwitchCommandRequest` becomes `AppEvent::SwitchChanged { object_id, state }` and is **not echoed**; the built-in mute switch is unchanged. `AppCommand::ResendSwitch { object_id }` sends the stored state again even though it did not change, for a command the application refused or could not carry out (HA does not set a switch's state itself, so this gives it the real state again; **hypothesis, not verified in a real HA:** HA may drop a state equal to the one it holds, in which case its UI does not revert); an unknown id is ignored. The satellite daemon uses the generic switches for TV control (`tv_*`) and for `aec_enabled` and `music_enabled` (the satellite wrapper only whitelists, pre-checks busy and re-sends the stored state; the cooldown and the final busy check are in `ctl.sh config`; [ADR 0012](../decisions/0012-config-switches-in-ha.md)); the mute switch is always listed first (`tests/server_io.rs`, `satellite_e2e.py` rely on it).
    - **`TextSensorEntity`** (`ListEntitiesTextSensorResponse`): `icon`, `device_class`, `entity_category`. State: `AppCommand::SetTextSensor { object_id, state: Option<String> }`, `None` is `missing_state`.
    - **Application-owned selects.** `SelectEntity` has `entity_category` and `command_echo`. With `command_echo = false` a valid choice is only reported as `AppEvent::SelectChanged` (not stored, not echoed; the option is logged at debug only, never at info, since it may be an app title) and HA shows what the application reports with `SetSelect` or `AppCommand::ClearSelect` (missing state). `AppCommand::SetSelectOptions { object_id, options }` replaces the options; HA reads them when it lists entities, so a changed list **closes the HA connection** (HA reconnects at once and lists again) and the select has no state until the application sends one; the application decides when that is safe. A select must have at least one option.
    - **Music on the built-in player** (`Config::music: Option<MusicConfig>`, default `None`; milestone M2 of the [music plan](../design/music-playback.md), [ADR 0010](../decisions/0010-music-playback.md); implemented 2026-11-05 on the PC, **no TV, no real HA, no sound**). With `None` nothing changes: flags 5124, one ANNOUNCEMENT format, a media URL ignored. With `Some`, the flags are 153093 (adds PLAY_MEDIA 512, PAUSE 1, PLAY 16384, BROWSE_MEDIA 131072) or, with `MusicConfig::announce` (default true), 1201669 (adds MEDIA_ANNOUNCE 1048576); sums checked against aioesphomeapi 46.6.0's `MediaPlayerEntityFeature` (fake-HA scenario K1). No VOLUME_MUTE, no MEDIA_ENQUEUE (D13, D12). `supported_formats` gets a second entry after the ANNOUNCEMENT one, purpose DEFAULT (`MusicConfig::format`: `flac` or `wav`, default flac, 48000 Hz, 2 channels, 2 bytes; `Config::validate` rejects MP3 and anything else, `ConfigError::InvalidMusic`). Commands: `play_media` becomes `AppEvent::Music(MusicCommand::Play { url, announce })`, `PAUSE` becomes `MusicCommand::Pause`, `PLAY` becomes `MusicCommand::Resume`, `STOP` stays `AppEvent::MediaStop` and volume stays `AppEvent::VolumeChanged` (shared reply and music volume, D2). `ENQUEUE` (HA sends it with a URL although MEDIA_ENQUEUE is not offered) is refused: the state is echoed and `MusicCommand::EnqueueRefused { url }` hands the URL up so the application can open and close it to free HA's proxy slot (D12). A media URL (play or enqueue) on a **plaintext** session is refused with a log line and no event unless `MusicConfig::allow_plaintext` (D14; pause and play are not URLs and still arrive); an announce play while `announce` is off, an empty URL, mute, seek and toggle are ignored. State: `AppCommand::SetMusicState(MusicState::{Idle, Playing, Paused})`, merged with the voice state (a reply or announcement reads `playing` over any music state), sent on change and on subscribe, with the shared volume; ignored with a log line when music is off. The server fetches and plays nothing and never logs or `Debug`-prints a URL. Tests: `entities.rs`, `config.rs` and `app.rs` unit tests, six `tests/server_io.rs` tests (music off, flags and formats, commands on a Noise session, announce not offered, plaintext refusal and `allow_plaintext`, state merge), fake-HA scenario K (`fake_device --music [--music-format flac|wav] [--music-no-announce] [--music-allow-plaintext]` and the stdin command `music idle|playing|paused`).
    - **Application-owned media players** (`MediaPlayerEntity`, `Config::media_players`; added 2026-11-04 for the TV, [ADR 0007](../decisions/0007-tv-media-player.md)): listed right after the built-in player, with their own object id and key. **Control only**: no `supported_formats` (so HA 2026.10.4 never takes the TTS or announcement format from them, nor proxies media to them) and `feature_flags` limited to `entities::APP_MEDIA_PLAYER_FEATURES` (pause, volume set, mute, turn on, turn off, volume step, stop, play); `Config::validate` rejects `PLAY_MEDIA`, `MEDIA_ANNOUNCE`, `BROWSE_MEDIA`, `SELECT_SOURCE` and every other bit. `MediaPlayerCommandRequest` is **routed by key**: the built-in key keeps the reply-volume behaviour (it used to ignore the key); an application key becomes `AppEvent::MediaPlayerCommand { object_id, command: PlayerCommand }` only for advertised features (a media URL is ignored with a log line, an unadvertised command is answered with the last state), and is **not echoed**. State: `AppCommand::SetMediaPlayer { object_id, status: PlayerStatus }` (`PlayerState` idle, playing, paused, on or off, the only states HA maps; `volume: Option<f32>`, `None` sent as NaN, which HA shows as no level; `muted`), not repeated when unchanged, re-sent on subscribe. There is **no unknown state**: nothing is sent until the application reports one, and the last one stays. Source selection is impossible: `api.proto` has no source list, and HA's ESPHome platform drops `SELECT_SOURCE`.
    - **Availability.** The native API has no per-entity "unavailable": HA marks all entities of the device unavailable while it is disconnected. The only per-entity signal is `missing_state` ("unknown"), which is what an entity shows until the application has reported a state. Commands for unknown keys are ignored, and keyless pairing sessions never see any entity.
    - `AppEvent` and `AppCommand` lost their `Eq` impls (they now carry `f32`); `PartialEq` remains.
  - **Listening indicator** (satellite, always on, not part of this crate): two `binary_sensor` entities "Listening" (`listening`) and "Microphone muted" (`microphone_muted`), see [Listening indicator](../development.md#listening-indicator).
- **Wake words:** `VoiceAssistantConfigurationResponse` reports no available or active wake words and `max_active_wake_words = 0`. The wake word is whatever the selected HA pipeline configures.
- **Encryption:**
  - With `noise_psk` set, the device accepts only Noise. Plaintext clients get the Noise-framed rejection, which HA reports as "requires encryption" and answers by asking for the key.
  - With `provisioning` set (and no `noise_psk`), HA sets the key itself: see [Pairing](#pairing-ha-driven-key-provisioning).
  - With neither, the device serves plaintext only (development). `api_encryption_supported` is then false, so HA never tries to provision a key.
- **One HA client at a time.** A new connection that completes its handshake replaces the old one. Keyless pairing sessions are the exception: they never replace it (below).
- **Retry policy:**
  - A run that ends with `ERROR`, or without progress (no `WAKE_WORD_END` or `STT_END`), delays the next wake word start by 250 ms × 2ⁿ.
  - Configuration errors (`*-missing`, `*not-found*`) use 2 s × 2ⁿ instead.
  - The delay is capped at 60 s.
  - HA's start reply must arrive within 10 s.
- **mDNS:** optional (`Config::mdns`, cargo feature `mdns`, on by default). It advertises `_esphomelib._tcp` with TXT records `friendly_name`, `version`, `mac`, `platform`, `board`, `network` and `api_encryption`, using `mdns-sd`. If the advertisement fails, the server logs a warning and keeps running.

## Pairing (HA-driven key provisioning)

Status: **implemented (2026-11-02), tested on a PC against aioesphomeapi 46.6.0 acting as HA and once against a real HA 2026.10.4 on the PC; verified on c3-a with the owner's HA 2026.10.4** ([P3 TV verification](../discovery/c3-a/P3-tv-verify-aec-pairing.md#3-pairing-on-the-tv-with-the-owners-ha)), except two points changed afterwards and **not yet re-verified with a real HA**: the deferred `PROVISIONING_CLOSED` disconnect and the key clear by the key holder (both below). Design and threat model: [install and configuration UX](../design/install-and-config-ux.md#5-pairing-mode-design-option-c-detail). Code: [`pairing.rs`](../../crates/esphome-api/src/pairing.rs) (pure state machine and key file), [`server.rs`](../../crates/esphome-api/src/server.rs).

`Config::provisioning = Some(Provisioning { key_file, window, open_at_start })` with `noise_psk = None`:

- **Start.** The server reads `key_file`. A valid key means paired (Noise with that key, as a fixed key). No file means unpaired. A corrupt file (not base64 of 32 non-zero bytes) stops `Server::bind` with an error instead of silently reopening pairing. `Server::needs_pairing()` tells the application to keep the microphone closed.
- **Window.** Opened at `run()` when unpaired and `open_at_start`, or by `AppCommand::OpenPairingWindow`. Closes after `window` (in memory only, so a restart reopens it if `open_at_start`) or when a key is accepted. `AppCommand::ResetPairing` deletes the key file, closes every session and reopens it. After a clear by the key holder (below) the window stays closed and is not opened at start either, until `OpenPairingWindow` or `ResetPairing`. Changes arrive as `AppEvent::Pairing(PairingEvent::…)`: `WindowOpened`, `WindowClosed`, `Paired { client_info, peer }`, `KeyRotated`, `Reset`, `Cleared { client_info, peer }`.
- **Keyless sessions** (unpaired only). The first byte selects plaintext or Noise with the all-zero PSK, as ESPHome does. Each keyless session runs in its own task (at most four) and never becomes the main session, so the voice state machine, the entities and microphone audio are unreachable without a key. It answers `HelloRequest`, `DeviceInfoRequest` (with `api_encryption_supported` and `api_encryption_provisionable` set and `voice_assistant_feature_flags = 0`), `ListEntitiesRequest` with only `ListEntitiesDoneResponse` (HA lists entities before it provisions), ping, disconnect and `NoiseEncryptionSetKeyRequest`. Voice, switch and media player messages are logged and ignored. While the window is closed, a new connection gets its `HelloResponse` and then `DisconnectRequest(reason = PROVISIONING_CLOSED)`, which HA's config flow reports as "closed its setup window"; existing keyless sessions are closed when the window closes. The `DisconnectRequest` waits for the client's next message (HA's flow sends `DeviceInfoRequest` once `connect()` returned) or 2 s, then the server waits up to 1 s for the `DisconnectResponse`. Reason: aioesphomeapi 46.6.0 raises the `ConnectionClosedEvent` that carries the reason only if the connection was already `CONNECTED` (`was_connected` in `_cleanup`), and the state becomes `CONNECTED` only when `connect()` resumes after the `HelloResponse`. If both frames arrive in one read, the disconnect is handled first, `connect()` fails without the event and HA 2026.10.4's `_fetch_device_info` returns `connection_error`. That is what the owner's HA in its pod showed 4 of 4 on c3-a; the fake-HA scenario F reproduces it with a proxy that batches the device's frames (6 of 6 `connection_error` before the change, 6 of 6 `provisioning_closed` after).
- **`SetKey`.** The key field holds base64 text, as HA and ESPHome use it. Accepted only from a zero-PSK Noise session while the window is open, at most one attempt per second (any session): base64 of exactly 32 bytes, not all zero, not empty. The key is written to `key_file` atomically (exclusive temporary file with mode 0600 in the same directory, `fsync`, `rename`, directory `fsync`, base64 plus a newline, the `noise_psk_file` format). Then the reply `success = true` is sent, the key is activated, and every session opened before it gets a `DisconnectRequest` and is closed (ESPHome does this 100 ms after its reply): keyless sessions at once, the main session (a rotation or clear on it) after its client disconnected by itself or after 500 ms, answering only disconnect and ping meanwhile, because HA's `cli.disconnect()` follows the reply at once and would otherwise race the server's request. HA then reconnects with the key. A storage failure answers `success = false` and keeps the device unpaired.
- **After pairing.** Plaintext and zero-PSK clients are refused as with a fixed key ("requires encryption", "Handshake MAC failure", which HA reads as "already has an encryption key"). A session that proved the key may **rotate** it with a new valid key (ESPHome behaviour; HA 2026.10.4 does not do this). Setting the current key again answers success and changes nothing. A key fixed in the configuration is never changed or cleared (ESPHome: "Key set in YAML").
- **Clear by the key holder.** An empty key from a session that proved the stored key (HA 2026.10.4 `_async_clear_dynamic_encryption_key`, run when the entry is deleted) is accepted, as ESPHome does: the server writes the marker `<key_file>.cleared` (mode 0600), deletes the key file, answers `success = true` (HA then removes its stored key), closes the sessions as above and emits `PairingEvent::Cleared`. It is then unpaired with the window **closed**. The marker keeps it closed across restarts (`Server::bind` ignores `open_at_start` while the marker exists and no key is stored); `OpenPairingWindow`, `ResetPairing` or a new key remove it. If the marker cannot be written or the key cannot be deleted, the reply is `success = false` and the key stays. An empty key from a keyless session (unpaired: nothing to clear) is refused, and a clear counts against the one-attempt-per-second limit.
- **Logging.** The key is never logged or put in `Debug` output: `KeyState`, `Transport` and `Refusal` redact or omit it, and refusals name the reason only. Logs contain the peer address, the client info and the key file path.
- **mDNS** (when enabled) follows the runtime state: TXT without `api_encryption` while the window is open, with it once a key is active, and no advertisement while unpaired with the window closed. Unverified on a TV.

Divergences from ESPHome 2026.10.1 (all deliberate):

| ESPHome | This crate | Why |
| --- | --- | --- |
| A keyless device is a full plaintext device (entities, voice) | Keyless sessions get identity, an empty entity list and `SetKey` only | No microphone access or control without a key ([design rule 1](../design/install-and-config-ux.md#52-rules)) |
| `SetKey` accepted over plaintext (deprecated, "will be removed in 2027.2.0") | Refused over plaintext | The key would cross the LAN in clear; HA 2026.9+ uses the zero-PSK path when `api_encryption_provisionable` is set |
| Empty key clears the key from any session that reached `SetKey` | Only from a session that proved the stored key; never with a key from the configuration | Same effect for HA (entry removal clears both sides); nobody without the key can unpair the device |
| After a clear the device is keyless and, with the provisioning window already satisfied, accepts keyless sessions until the next reboot | Unpaired with the window closed, persisted in `<key_file>.cleared`, until a local open or reset | A removed device must not be claimable by the next LAN peer; HA sends the clear when its entry is deleted, not to re-pair |
| Closed window: `DisconnectRequest(PROVISIONING_CLOSED)` right behind the `HelloResponse` | After the client's next message, or 2 s | The back-to-back frames race in aioesphomeapi 46.6.0 and HA shows `connection_error` (c3-a P3) |
| Disconnects every client 100 ms after a key change | Keyless sessions at once (verified with HA on c3-a); the main session after the client's own disconnect or 500 ms | HA disconnects right after the `SetKey` reply; answering it avoids a race |
| `provisioning:` window is optional; without it a keyless device accepts a key forever | The window is mandatory (1 s to 1 day) | Bounded exposure |
| Multiple concurrent API clients | One main session plus up to four keyless sessions | Existing single-client design; HA needs two keyless sessions at once (main and zero-PSK) |
| `voice_assistant_feature_flags` as configured | 0 on keyless sessions | HA creates no satellite before a key exists |

## Timers

Status: **implemented in the API crate; the satellite advertises it by default (`[device] timers = true`) and rings an alarm when a timer finishes (2026-11-04, PC only: unit tests, fake-HA harness; not yet heard on a TV).** Verified against aioesphomeapi 46.6.0 acting as HA, not against a real HA. HA's own code was read on the owner's HA 2026.10 (pod `home-assistant-hass-0`, read-only).

How HA behaves (HA 2026.10.4 `esphome/assist_satellite.py`, `intent/timers.py`; source reading):

- When the device advertises `TIMERS` (bit 8) in its voice feature flags, the ESPHome integration registers a timer handler for the device. It forwards each HA intent timer event as a `VoiceAssistantTimerEventResponse` with `timer_id`, `name`, `total_seconds` (the created seconds, which grow when time is added), `seconds_left` and `is_active`.
- The event types are `STARTED` (timer created), `UPDATED` (time added or removed, paused, resumed; a pause is `UPDATED` with `is_active = false`), `CANCELLED` and `FINISHED`.
- HA owns the timers and counts them down. The device never reports timers back. There is no message to list timers.
- HA does **not** replay existing timers when the device reconnects. After a reconnect the handler sees only later events. A device that wants to survive a reconnect must keep its own state.

What the crate does:

- Enable it with `Config::voice_features = features::DEFAULT_WITH_TIMERS` (31). The crate's default stays `features::DEFAULT` (23). `fake_device` takes `--features 31`. The satellite sets TIMERS unless `[device] timers = false` (and optionally `start_conversation = true`, which needs `announce = true`); see the configuration reference in [development.md](../development.md#configuration-reference).
- With TIMERS advertised, each HA timer message becomes `AppEvent::Timer { event: TimerEvent, id, name, total_seconds, seconds_left, is_active }`. Unknown event types are dropped with a debug line. Without TIMERS the messages are ignored.
- `AppEvent`'s hand-written `Debug` prints event, id and seconds only. The timer name is user speech and stays out of logs (`name_bytes` in `Timer`'s `Debug`). `AppEvent` was already `#[non_exhaustive]`, so adding the variant breaks no match.
- `TimerTable` is an optional helper for the application: `apply(&AppEvent, Instant)` keeps the timers HA reported (at most 64), `Timer::remaining(now)` counts down locally while the timer is active, and `by_remaining` lists them soonest first. It lives in the application and so survives HA reconnects, which is the only state recovery available given that HA does not replay. The server itself keeps no timer state.
- The satellite keeps a `TimerTable` (survives HA reconnects) and logs each event at info level (`timer <event> id=... seconds_left=...`, so a finished timer logs `timer finished id=... seconds_left=0`; never the name). It rings an alarm on `FINISHED` (see below). `satellite_e2e.py` checks this with a daemon on the default config plus `start_conversation = true` (flags 63).

### Timer alarm (satellite, 2026-11-04)

What HA does and does not do (HA 2026.10, `intent/timers.py` and `esphome/assist_satellite.py`, read on the owner's HA):

- `_timer_finished` **pops the timer from HA's table before** calling the device's handler. After `FINISHED` the timer no longer exists in HA: it cannot be cancelled, and no `CANCELLED` or `UPDATED` follows for it. "Cancel the timer" by voice does nothing for a ringing alarm.
- HA has **no "stop ringing" message** to the device; ESPHome devices stop their own sound (a button, or an on-device "stop" wake word). So stopping is the satellite's job. A timer created with a conversation command (`conversation_command`) runs that command and sends the device no `FINISHED`.
- With TIMERS advertised HA needs **no other setup**: `HassStartTimer` works for the satellite's device (the Assist pipeline passes the device id). That is why `[device] timers` is now **on by default**. Without TIMERS HA answers that timers are not supported on this device. An already added device picks the flag up on its next connection (restart of the satellite or a reload of the ESPHome entry).

What the satellite does:

- **Start.** On `FINISHED` it plays a built-in chime (generated in code, no audio asset): a falling "ding-dong" (C6 then G5, bell-like partials, about 0.7 full scale before the volume) twice, then a pause, a 2.6 s cycle, repeated. It is streamed to `pacat` (16 kHz mono, stream name `timer-alarm`, same `sink.latency_msec`) paced a little ahead of real time, so a stop or a volume change is heard within about half a second.
- **Volume.** The reply volume (the media player slider in HA, default 40 % = -30 dB) times `sink.gain`, read for every slice. At 0 % the alarm is silent (a warning is logged). The TV's own volume is never touched. The microphone mute and the kill switch are **not** applied to the alarm: they close the microphone, not the speaker, and announcements already play while muted (a timer you set is something you asked for). With the alarm off, set `timer_alarm_max_s = 0`.
- **Cap.** It stops by itself after `[device] timer_alarm_max_s` (default 300, at most 3600; 0 = no sound). A second timer that finishes while it rings joins it and restarts the cap.
- **Stop.** The wake word detected by HA (`WakeWordDetected`) or a run that starts at speech-to-text (push-to-talk) stops it before the pipeline streams; the HA button entity **Stop timer alarm** (`stop_timer_alarm`); the media player's stop (`AppEvent::MediaStop`); HA cancelling or updating the timer that rings (a defensive path, see above); the cap. HA's abort and stop messages for replies (`StopPlayback`) leave it alone, and an HA disconnect does not stop it.
- **Queue.** If a reply or announcement is playing, or a conversation run is in progress, when a timer finishes, the alarm waits (state "queued") and starts when both are over, still counting its cap from the finish. If an announcement or reply arrives while it rings, it takes the speaker (never two `pacat` streams) and the alarm resumes afterwards. After a reconnect nothing is replayed: HA sends nothing for timers already finished.
- **Entities (when `timers` is on).** Text sensor **Timers**: `none`, `ringing`, or `N timer(s), next in M min` (rounded up, `(paused)` when the next one is paused); binary sensor **Timer alarm** (on from the finish until it stops, including while queued); the button **Stop timer alarm**. With `timer_alarm_max_s = 0` only the Timers sensor exists. They are state of what HA told the satellite: a disconnected HA cannot send `FINISHED` and the satellite does not sound timers on its own.
- **Logs.** `timer alarm: ringing for at most N s`, `timer alarm stopped (<reason>; was Ringing)`, `timer alarm paused: a reply or announcement is playing`, `timer alarm: stopped at the time cap`, `timer alarm: chime ended (...)` and failures. Never the timer name.

Not verified on a TV: how the chime sounds at 40 % and at other TV volumes, whether the server-side wake word reacts to the chime picked up by the microphone (the alarm rings while the wake word is armed), and the latency of the stop. See the checklist in [development.md](../development.md#timer-alarm).

## Capture liveness (`AppCommand::CaptureLive`)

A wake word session in HA (our `VoiceAssistantRequest{start: true}` with `USE_WAKE_WORD`) must exist only while audio really flows into it. **Why (documented, HA 2026.10.4 source read in the pod; the full chain was not instrumented):** `assist_satellite.announce`, `start_conversation` and `ask_question` first await `_cancel_running_pipeline()`, which cancels the pipeline task and waits for it. The Wyoming wake word client in that pipeline, on cancellation, waits in `finally: await audio_task` for the **next audio chunk**. A session whose device sends nothing (c3-b with LG hands-free holding the PCM) therefore blocks the announcement for good ([c3-b P4 finding 1](../discovery/c3-b/P4-sound-session.md)). ESPHome's own `_abort_pipeline` (a `VoiceAssistantRequest{start: false}` from the device) puts an end marker in the audio queue before cancelling, so an abort from the device is safe at any time.

- **Input.** The application tells the server with `AppCommand::CaptureLive(bool)` whether its capture delivers audio. A host that never sends it counts as live (the `fake_device` example and library users keep their old behaviour). The satellite daemon sends `false` before it starts the capture thread; the capture thread sends `true` after the PCM is open and a read returned frames (a file mic: at the open) and `false` as soon as the PCM is closed or stops delivering: mic busy or not found, HA mute switch, kill switch, firmware guard, "not paired", the self-check closing the mic, a stall or a read error with its reopen backoff, shutdown. It travels in the same command stream as the audio and the indicator sensors, so `true` comes right after "Listening" ON and before the first chunk, and `false` before "Listening" OFF.
- **Voice layer.** `false`: a starting or running run is aborted (`VoiceAssistantRequest{start: false}`, streaming stops, as with the mute switch), a retry backoff is cancelled, a reply that is playing finishes, an announcement is left alone, and nothing is requested: `Voice::start` does nothing while the capture is not live, so a re-arm after a reply or announcement, a `continue_conversation` or `start_conversation` follow-up, a backoff retry and an HA re-subscribe all wait. Push-to-talk is ignored with a warning. `true`: an armed wake word is requested at once. The Listening indicator is not touched by any of this (it stays tied to the PCM).
- **Announcements** therefore find no session to cancel in every state where the mic is not delivering, and in the capturing state the cancel completes on the next chunk (32 ms).
- **Tests.** Voice unit tests (`voice::tests::*capture*`, announcement ones), `capture::tests::capture_live_follows_whether_audio_flows` (busy, mute, firmware, not-paired and kill-switch gates against the command stream), the scenario `L` of `fake_ha.py` (the fake HA models HA's cancel: an announcement while a session is open and no chunk arrives counts as hung) and `satellite_e2e.py` BM1 to BM12 against the real daemon with a missing mic file. Not verified on a TV.

### Ending the audio from the device (`AppCommand::EndAudio`)

For hold-to-talk (the [Magic Remote's mic button](../design/remote-mic-button.md)) the application ends the audio of the run that streams with `AppCommand::EndAudio`: the server sends `VoiceAssistantAudio{end: true}` (HA's `handle_stop(False)`: speech-to-text finalizes, the run goes on to the intent and the reply) and the application gets `StopStreaming`. Unlike `StopPipeline` it does not abort the run or disarm the wake word; with nothing streaming it is ignored. Send it after the run's last `Audio` chunk on the same channel. Tests: `voice::tests::end_audio_*`. Not verified with a real HA.

To tell its own run from others, the application gets `StartStreaming { push_to_talk: true }` only for the run of the last `StartPipeline(PushToTalk)` (a `continue_conversation` follow-up, a `start_conversation` run and wake word runs carry `false`), and `AppEvent::PushToTalkFailed` once for a request that will not stream: refused (muted, no live capture, an announcement, not subscribed) or dropped before it streamed (HA's error answer or no answer within 10 s, an announcement, mute, capture loss, a disconnect, `StopPipeline`, a wake word session replacing it). A newer request replaces a waiting one without a report. Tests: `voice::tests::*push_to_talk*`.

### An announcement is not a failed run

HA's announcement, a timer alarm and other services first cancel the idle wake word pipeline; HA ends it with `RUN_END` and no error. Until 0.2.2 the voice layer counted any run without progress as a failure, so the retry delay doubled with every announcement (250 ms up to 60 s, reset only by a wake word) and after about eight announcements the satellite stopped listening for up to a minute after each one ([c3-b P4 session 2](../discovery/c3-b/P4-sound-session.md)). Now only a run that ended with an HA **error** counts (`Voice::fail`, the backoff of the first section). A run HA ended without error and without a wake word or transcript is a *soft end*: it leaves the failure counter alone and the wake word is requested again after 250 ms; an announcement resets the soft-end counter and re-arms the wake word right after its playback. Only a stream of soft ends with no announcement between them (more than 3 in a row) slows down with the same doubling, so a misbehaving HA cannot cause a hot loop; a wake word or transcript resets it. Tests: `voice::tests::many_announcements_*`, `a_run_ended_by_ha_without_error_*`, `runs_ended_by_ha_again_and_again_*`; `fake_ha.py` L13 (12 announcements in a row, wake word back within 1 s each time) and `satellite_e2e.py` BM13 and BM14 (10 against the real daemon, no `run failed` in its log).

## START_CONVERSATION status

Status: **works in the implementation, tested with aioesphomeapi 46.6.0, off by default in the advertised flags; the satellite behaves the same either way.** Not yet exercised against a real HA.

- HA side (`assist_satellite.py`): `assist_satellite.start_conversation` calls `async_start_conversation`, which is `_do_announce(..., run_pipeline_after=True)`. It sends `VoiceAssistantAnnounceRequest` with `start_conversation = true` and waits for `VoiceAssistantAnnounceFinished`. HA adds the `START_CONVERSATION` supported feature to the satellite entity only when the device advertises bit 32. Without the bit, HA does not offer the feature for this entity (the service gating itself is in the `assist_satellite` component, which was not read).
- Device side: `Voice::on_announce` aborts any run, plays the announcement (`AppEvent::Announce`, `start_conversation` flag), and after `AppCommand::AnnounceFinished` sends `AnnounceFinished` to HA and then starts a run without wake word (at STT) instead of re-arming. This happens regardless of the advertised bit, because the request itself carries the flag. Harness check A21 covers it (announce, then a run with `USE_WAKE_WORD` unset, then re-arm after `RUN_END`).
- So, to let `assist_satellite.start_conversation` be called for the TV, advertise bit 32 (`features::DEFAULT | features::START_CONVERSATION` = 55). `ANNOUNCE` (16) is also needed because HA waits for the announcement first. Announcements still arrive as URLs, which fail while HA's internal URL is unreachable from the TV (see the announcement note under the open points).
- Not verified: the real HA flow end to end (including HA's 5 minute announcement timeout, `_ANNOUNCEMENT_TIMEOUT_SEC`, when playback fails) and the TV audio path for the announcement.

## Existing crate vs own implementation

`esphome-native-api` 3.0.0 (UbiHome, 2026-07) was evaluated:

- **For it:** MIT licence, maintained, client and server roles, Noise via `noise-protocol`. Unknown message types are now skipped.
- **Against it:**
  - It ships generated protos only up to ESPHome 2026.6.2, not 2026.10.x.
  - It uses prost 0.13 and enables tokio `full`, which adds a multi-thread runtime to a static TV binary.
  - It provides message types but no voice-assistant flow: no pipeline state machine, retry, announce or TTS streaming handling.
  - Its message type table is hand-written.

**Choice:** a thin implementation of our own, about 2.5 k lines including doc comments, plus tests, on the pinned proto, `prost` 0.14, `snow` and tokio `current_thread`. The protocol surface is small. The voice state machine is the part that matters, and it has to be ours either way.

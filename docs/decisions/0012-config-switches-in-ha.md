# ADR 0012: Echo cancellation and music as Home Assistant config switches that run `ctl.sh config`

- **Status:** Accepted (2026-11-06, owner). Implemented on the host (unit tests, `server_io` test, `tv_settings.sh`); **not run on a TV and not seen in a real HA**. Amends the scope of [ADR 0011](0011-aec-on-by-default.md) decision 3 (the settings toggle) and of [ADR 0010](0010-music-playback.md) D7 (the music default and how it is changed).

## Context

- 0.4.4 added two TV app controls, echo cancellation and music, both run as `ctl.sh config aec|music on|off`: it edits `[aec] enabled` or `[music] enabled` in `etc/config.toml`, checks the new file with `--check-config`, restarts the daemon and puts the previous config back if the daemon does not come back. The daemon reads both keys at start only.
- The owner wants the same two controls on the device page in Home Assistant, as `switch` entities with `entity_category: config`.
- [ADR 0008](0008-user-initiated-lg-settings.md) decision 3 says the daemon never changes the two **LG** settings and that the write path is `ctl.sh set`. These two switches change the **satellite's own** config, not an LG setting, and `ctl.sh config` is a separate command from `set` on purpose (review C7: nothing the phone setup server can run restarts the daemon, `packaging/webos/tests/no_self_stop.py`). Both stay as they are.

## Decision

1. **Two switches**, object ids `aec_enabled` ("Echo cancellation", `mdi:waveform`) and `music_enabled` ("Music playback", `mdi:music`), entity category `config`. They are generic `SwitchEntity` entries listed after the built-in mute switch (which stays first) and after the TV control and compatibility entities. State is the config value the running process started with (`settings.aec.enabled`, `settings.music.enabled`), sent after the server starts and again at every HA subscribe (the server keeps it).
2. **A change runs `ctl.sh config <aec|music> <on|off>` detached**, in a session of its own (`setsid nohup sh`, the way `start.sh` starts the daemon), because `ctl.sh` stops the daemon that started it. It runs with an **empty environment** plus a fixed `PATH`, `WEBOS_SAT_PREFIX` (the install directory, the parent of the config's `etc/`, so daemon and `ctl.sh` act on the same install) and `WEBOS_SAT_SOURCE=ha` (the history line in `etc/tv-settings.log` then says `source=ha`; any other value is logged as `ctl`), the way `ctl.sh` starts the setup server. In particular it does **not** inherit `WEBOS_SAT_LOCK_HELD`: that variable is exported by `lock_take` to the children of whoever holds the install lock, and a daemon started under `ctl.sh start` or an update would otherwise pass it on, making this `ctl.sh` skip the lock. `start.sh` also unsets it before it launches the daemon or the supervisor. The script path and the three arguments are fixed: the object id maps to `aec` or `music` through a table, the state to `on` or `off`, and no received text is part of any argument or of the `sh -c` text. `ctl.sh` is found as `bin/ctl.sh` next to the config's `etc/` directory (the place the default `report.dir` already uses); without that file the two entities are **not listed** (nothing is "unavailable"), which is the case on a PC.
3. **Guards live in `ctl.sh config`, so every entry point behaves the same** (owner decision, 2026-11-06, after a design review: the first version kept the cooldown and the activity refusal in the daemon's wrapper only, so the TV app, which runs the same command, had neither). In `ctl.sh config`, in this order: install lock, check of the current config, `already` (a request for the state in force does nothing, also inside the cooldown), **cooldown**, write the new file and check it with `--check-config`, **busy**, stamp, rename over the config, restart with rollback, history line, one JSON line. The config itself is not touched before the guards pass: the new file is written next to it (and removed again on a refusal) before the busy check, because the busy check follows `--check-config`. A refusal changes nothing and writes no history line.
   - **Cooldown:** at most one change per 30 s. The time of the last change is kept in `run/config-change.stamp` (unix seconds, atomic write, mode 0600), written just before the config is renamed (whether or not a restart follows), because the change restarts the daemon and a new process has no memory. It blocks while `t <= now + 30 && now < t + 30`; a missing, garbled or far-future (more than 30 s ahead) file blocks nothing. If it cannot be written the result is `failed` ("cannot write the cooldown file") and nothing is changed. There is no environment variable that bypasses it (the host tests delete the stamp between changes).
   - **Busy:** the daemon writes `"busy":"voice"|"music"|"alarm"|null` into `run/voice.json` (voice: a conversation or a reply or announcement playing; music: loaded, playing or paused; alarm: the timer alarm queued or ringing; checked in that order: one definition in the daemon, used for the file and for HA's pre-check). `ctl.sh` reads it only when the daemon is running and the file is fresh (60 s); a missing, stale or null field (an older daemon, a daemon that is down) proceeds. The check runs after the new config has passed `--check-config` and before the stamp and the rename; a refusal removes the temporary file and nothing else.
   - **Result fields:** the JSON line (schema stays 1) gains `"reason":""|"cooldown"|"busy"` and `"retry_in_s":N|null` (seconds left, for `cooldown`), appended last. `result` stays `applied|already|refused|failed`. Texts: "the last change was N s ago; try again in M s", "a voice request is in progress", "music is loaded (playing or paused)", "a timer alarm is active".
   - **What the daemon keeps:** the whitelist (two object ids, fixed arguments, fixed environment), a busy pre-check from its own state (so a refused request does not even start a process), a request for the state already in force (an optimization: `ctl.sh` answers `already` for it too, not a separate rule), and one `ctl.sh` in flight (it stays in flight until the script has exited; after 120 s a still-running script is logged, not killed: it may sit between two config files). The daemon has no cooldown of its own and no stamp file.
   A refused request, a failure to start `ctl.sh`, and a `ctl.sh` that ends while this process lives (it failed, refused, or changed nothing) make the server **send the stored state again** (`AppCommand::ResendSwitch`; HA does not change the state itself); a refusal reported by `ctl.sh` takes the same path through the task that reaps the script. **Hypothesis, not verified in a real HA:** that resend makes HA's UI show the old state again; HA may drop a state equal to the one it holds.
   `ctl.sh`'s one JSON line goes to `run/config_switch.out` (a file, not a pipe: the restart ends this process and a closed pipe would kill the script). Only its `result`, `daemon`, `error` and `reason` fields are logged (error cut to 160 printable characters), by the task that reaps the script or, after a restart, by a task of the new process that looks at the file every 5 s for up to a minute (the script prints its line only after `start.sh` has returned, so a read at start-up would find it empty and report it at the next start as the last change). A `result` of `already`, or `applied` with `daemon` `not running`, while this process lives is logged as a warning that nothing was restarted and the config and the running process now differ. A successful change restarts the daemon; HA reconnects and reads the new state, and for music the new media player flags.
4. **Logging:** the object id and the result only, never speech, audio or a URL. `ctl.sh` keeps its own history line in `etc/tv-settings.log`.
5. **Unchanged:** the phone setup server cannot run `config` (no `config` in its argument builder, `no_self_stop.py` passes); the TV app and SSH use the same command; `status --json` still reports `aec_enabled` and `music_enabled`.

## Consequences

- HA gets a way to restart the satellite (a few seconds without listening) and, with `music_enabled`, to switch on the fetch of stream URLs by a daemon that runs as root. This is no new class of power: the same paired HA can already start voice runs, play announcements and, with music on, play URLs; the fetch guard and the plaintext refusal of [ADR 0010](0010-music-playback.md) apply unchanged. Whoever controls the paired HA, or has the key, can now also change these two keys. The switch is off by default for music, as before.
- A flip in HA, or a press in the TV app, is refused while anything audible runs or within 30 s of the previous change; the refused request is answered with the stored state (whether HA's UI reverts at once is unverified, see 3).
- The detached child outlives the daemon on purpose. `ctl.sh` takes the install lock itself (60 s wait), so it cannot run beside an update, a TV app change or another config run. If it hangs, this process keeps it in flight and refuses further changes, and the 30 s cooldown (in `ctl.sh`, kept in a file) holds across the restart a successful change causes and for the TV app too, so a flapping HA automation can change the config at most every 30 s (each change still restarts the satellite).
- **Residual window:** the busy check in `ctl.sh` reads `run/voice.json`, which the daemon rewrites within about 1 s of a change (it is checked once a second, not per audio frame), and it is made before the restart, not again when the daemon is stopped (about 1 to 2 s later). Something that starts in that window (up to about 1 s of `voice.json` delay plus the restart's own 1 to 2 s) is cut off by the restart. Re-checking at the moment of the stop would need a way for the shell script to ask the daemon; not built.
- **Residual risk, flapping automation:** the daemon has no cooldown pre-check of its own (deliberate, see decision 3), so a HA automation that flips a switch repeatedly costs one `ctl.sh` start and one `--check-config` per flip inside the cooldown, at most one at a time (the in-flight rule); each refused one is answered with the stored state.
- Not verified on a TV: the real `setsid`, the restart from inside the daemon's own session, the cooldown stamp across it, and HA's display of the reverted state.

## Alternatives considered

- **The daemon rewrites the config and re-executes itself:** duplicates the checked, rolled-back logic of `ctl.sh config` in a second place; rejected.
- **Guards only in the daemon's wrapper (the first version):** the TV app runs the same `ctl.sh config` and would have had neither the cooldown nor the busy refusal; two entry points with different rules for one transaction; rejected.
- **Rust port considered and rejected (owner decision, after the design review).** (b) A config-only Rust subcommand (the guards and the file rewrite in the binary, `ctl.sh` calling it) splits one transaction (lock, check, rewrite, restart, rollback) across two languages and still needs the binary to be present and healthy. (c) A full port of `ctl.sh config` breaks install, rollback and recovery exactly when the binary is broken (the case rollback exists for), and means rewriting about 1700 lines of shell tests and losing `no_self_stop.py`, the check that the phone setup server cannot reach a stop. If anything ever moves to Rust, it would be `status --json` with a shell fallback, under its own ADR.
- **Make `config` part of `ctl.sh set`:** would break C7 (the phone setup server could then stop the daemon and its own session); rejected.
- **List the switches as unavailable when `ctl.sh` is missing:** the protocol has no "unavailable" for a switch except `missing_state` (shown as unknown); not listing them is simpler and honest.
- **A `select` or a button pair:** a switch is what the TV app shows and what HA users expect for an on/off setting.

## Revisit when

- A TV run shows the detached start failing, a restart loop, or HA showing a wrong state.
- Another setting should be changeable from HA: add it to the table of fixed arguments only together with an owner decision.
